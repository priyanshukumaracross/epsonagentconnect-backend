# Epson Expert Connect: Backend API

REST API, live call queue and WebRTC call setup (signaling) for Epson Expert Connect.
**Node.js + Express + Socket.IO**, database **Neon (PostgreSQL)**, hosted on **Render** (free web service).

Related repositories: **website** (customer app, Vercel) and **admin** (admin panel + expert console, Vercel).

## Run locally

Requirements: Node 20+ and a Neon database.

```bash
cp .env.example .env     # set DATABASE_URL (Neon connection string) and JWT_SECRET
npm install
npm run dev              # http://localhost:4000
```

On start-up the server creates/updates the tables and, if no admin exists yet, creates one from `SEED_ADMIN_EMAIL` / `SEED_ADMIN_PASSWORD`.
Optional demo data (3 experts with password `Agent@123` + 3 stores): `SEED_DEMO_DATA=true npm run db:seed`.

| Script | What it does |
|---|---|
| `npm run dev` | Start with auto-reload |
| `npm start` | Start (used by Render) |
| `npm run db:migrate` | Create/update tables (also runs automatically on start) |
| `npm run db:seed` | Create the admin from `SEED_ADMIN_*` (+ demo data with `SEED_DEMO_DATA=true`) |

Check it's running: `GET /api/health` (add `?db=1` to also check the database).

## Deploy on Render (free)

1. Push this repository to GitHub.
2. **Neon**: open your project → **Connect** → copy the connection string (`postgresql://…sslmode=require`).
   You can use a separate Neon branch or database for production so test data stays out of it.
3. **Render** → **New → Blueprint** → select this repository. `render.yaml` sets up a free Node web service in the Ohio region, the same AWS region (us-east-2) as the Neon database.
4. Fill in the values Render asks for:

| Variable | Value |
|---|---|
| `DATABASE_URL` | Neon connection string |
| `CORS_ORIGINS` | your two Vercel URLs, comma-separated, e.g. `https://epson-connect.vercel.app,https://epson-connect-admin.vercel.app`. A wildcard inside a host name is allowed: `https://epson-connect*.vercel.app` covers both plus Vercel preview URLs |
| `SEED_ADMIN_EMAIL` / `SEED_ADMIN_PASSWORD` | the first admin login (created automatically on first start) |
| `TURN_URLS` / `TURN_USERNAME` / `TURN_CREDENTIAL`, `METERED_TURN_APP` / `METERED_TURN_API_KEY` | TURN relay (free, no card), needed for calls to work on every network (see below) |

   `JWT_SECRET` is generated by Render automatically.
5. Deploy. The URL looks like `https://epson-connect-api.onrender.com`. Open `/api/health` to check.
6. Put this URL in the **website** and **admin** Vercel projects as `VITE_API_URL`.

Every push to the main branch redeploys automatically.

### About the Render free plan
- **Render sleeps a free service after 15 minutes without traffic.** This backend prevents that by itself: every `KEEP_ALIVE_MINUTES` (default 10) it calls its own public `/api/health` URL, which Render provides as `RENDER_EXTERNAL_URL`. The log shows `✔ Keep-alive: pinging …` on start. The ping doesn't touch the database, so Neon can still sleep and save compute. Set `KEEP_ALIVE=false` to turn it off.
- Staying awake all month uses about 744 of the workspace's 750 free hours, so **keep only this one free service running in the Render workspace**. If the hours run out, Render suspends free services until the next month.
- When it sleeps or redeploys, anyone waiting in the queue is disconnected. Calls still waiting are marked `failed`, and calls in progress are closed as `completed`.
- It runs as **one instance**, which this app needs: who is online and the missed-call timers are kept in memory.
- The free plan includes 750 hours a month, enough for one service running all the time.

### Calls on every network: TURN relay
Audio and video go straight from browser to browser where possible. When the two sides are on different networks behind firewalls (mobile data, office Wi-Fi, an expert in Canada and a customer in India), there's often no direct path, and the call connects with no audio or video. A **TURN relay** passes the media through a server instead, so the call works on any internet connection. The browsers choose direct or relay automatically. Only calls that can't connect directly use relay bandwidth. A relayed video call uses about 1 GB an hour; a voice call uses about 0.05 GB.

Free options with no payment method. Set up both: every configured relay is offered, and the browsers use whichever gets through.

**1. ExpressTURN**: 1,000 GB a month free, fixed login, ports 3478 UDP/TCP.
1. Sign up at [expressturn.com](https://www.expressturn.com) (free plan) → dashboard.
2. Copy the server address, username and password into Render:
   - `TURN_URLS` = `turn:<server>:3478,turn:<server>:3478?transport=tcp`
   - `TURN_USERNAME`, `TURN_CREDENTIAL`

**2. Metered Open Relay**: 20 GB a month free, "no credit card required". Ports 80 and 443 plus TLS, so it gets through strict office and hotel firewalls that block port 3478.
1. Sign up at [dashboard.metered.ca/signup?tool=turnserver](https://dashboard.metered.ca/signup?tool=turnserver). You choose an app name, e.g. `epsonconnect` (→ `epsonconnect.metered.live`).
2. **TURN Server → API key** → copy it.
3. Render: `METERED_TURN_APP` = `epsonconnect`, `METERED_TURN_API_KEY` = the key. Optional: `METERED_TURN_REGION`, e.g. `global`.

Check: the log shows `✔ TURN relay ready (metered, static)` and `/api/health` shows `"turn":"metered,static"`. The API keys stay on the server; browsers only get the relay logins from `/api/public/ice`. If a provider can't be reached, it's skipped and the log shows a warning.

When usage grows, **Cloudflare Realtime TURN** (1,000 GB free, then $0.05/GB; needs a payment method on file) is also supported: `CLOUDFLARE_TURN_KEY_ID` and `CLOUDFLARE_TURN_API_TOKEN`.

**Dropped connections:** if a call's network path breaks mid-call, for example on a Wi-Fi ↔ mobile data switch, both browsers notice within a few seconds and reconnect the same call (an "ICE restart"), retrying every 10 seconds while the network is down.

## Database
Tables: `users` (admins and experts), `stores`, `leads` (customer form submissions) and `calls` (every call attempt).
The schema is in `src/db/schema.sql`. It's idempotent and applied on every start.

| Call status | Meaning | Call done? |
|---|---|---|
| `queued` | Customer waiting for an expert | — |
| `in_progress` | Expert and customer are talking | — |
| `completed` | The call happened | **Yes** |
| `missed` | No expert answered within `CALL_RING_TIMEOUT_SEC` | No |
| `cancelled` | Customer left before an expert answered | No |
| `failed` | Interrupted by a server restart while waiting | No |

## API overview

| Area | Endpoints |
|---|---|
| Public (customer) | `GET /api/public/stores/:code`, `GET /api/public/availability`, `GET /api/public/ice`, `POST /api/public/leads`, `POST /api/public/calls`, `POST /api/public/calls/:id/feedback`, `POST /api/public/calls/:id/requests` |
| Auth | `POST /api/auth/login`, `GET /api/auth/me`, `POST /api/auth/change-password` |
| Admin | `GET /api/admin/stats`, `GET /api/admin/calls`, `GET /api/admin/leads`, `GET /api/admin/leads/:id`, `GET /api/admin/export/calls.csv`, `GET /api/admin/export/leads.csv`, `GET/POST/PATCH /api/admin/users`, `GET/POST/PATCH /api/admin/stores` |
| Expert | `GET /api/agent/stats`, `GET /api/agent/calls`, `PATCH /api/agent/calls/:id/notes` |
| Socket.IO | customer: `queue:position`, `call:accepted`, `signal`, `call:end`, `call:ended`, `call:missed` · expert: `queue:update`, `agent:setStatus`, `call:accept`, `call:ready`, `signal`, `call:end` · admin: `calls:changed`, `agents:presence` |
